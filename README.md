# sim-engine

The earthmoving sim's rules, with no screens. "sim-engine" is a working name until the game has a real one.

The plan is in section 15 of the design document. Port the prototype one piece at a time, prove each piece plays the same as the prototype, and only then put screens on top.

## Running it

The game's screens are in `app/` (React, Vite). To play it in your browser:

```
cd app
npm install        # once
npm run dev        # then open http://localhost:5173
```

To look at later screens without playing up to them, open http://localhost:5173/?demo=council: a business that's run its own contract, with a council package and a flood recovery program out to tender.

The engine:

```
npm install        # once
npm test           # run the tests
npm run watch      # re-run the tests every time you save a file
npm run check      # type-check, then test: run this before every commit
```

## What's here

**Screens (`app/src`)**: `App.tsx` picks the screen; `store.ts` keeps the career, saves it on the device after every change and redraws; `screens/` has Setup, Shop, Game (header, tabs, dock, cards, the week's docket), Yard, and End. `prototype.css` and `icons.ts` are copied from the prototype by `scripts/extract-look.mjs`, so the look matches.

## Rules for the code

1. **Engine code never draws anything and never writes text the player reads.** It returns numbers and facts, such as `{ missedNow: true }`, and the screens turn those into words. That way wording can change without touching the rules, and the game can be translated later. Where a story is picked at random, the engine stores which one (a number) and the words live in `src/text/`. Don't reorder those lists: saved careers point into them by position. Names are data, not sentences, and can stay in the engine: places, client names, kinds of private job.
2. **Every roll uses the career's stream** (`fromState`), never `Math.random()`. The one exception is picking a new career's seed.
3. **Every ported piece gets a parity test** before anything is built on it, and the test is checked by breaking the rule on purpose and watching it fail. If you change a rule on purpose, change the test in the same commit and say why in the commit message.
4. **Small files, one topic each.**

## Where the real game differs from the prototype

The engine matches the prototype rule for rule, except where it does better. Each difference sits behind one switch,
`compat.prototype` in `src/compat.ts`. The game leaves it off. The side-by-side tests turn it on (`test/setup.ts`), so they
still check every rule against the prototype exactly. `test/fixes.test.ts` tests the differences themselves.

- **Fair shuffles.** The prototype shuffles with `sort(() => rand() - 0.5)`, which is biased (some orders come up far more
  often) and depends on the browser. The engine does a fair Fisher–Yates shuffle: which idle machines head contractors ring
  about, council package road names, flood program roads and lots, Charters Towers road names, and subbie quotes.
- **Subbie quotes have their own seed.** The prototype rolls them with `Math.random()` while it draws the screen. The engine gives each job's quotes a seed for the week, so they're the same every time you look.
- **A career replays from its seed alone.** The prototype picks which real year's rain a career replays with `Math.random()`,
  outside the career's seed. The engine takes it from the seed (or as a parameter, which the side-by-side tests use).

Still open:

- The whole-career test plays a simple bot (first choice on every card). It never reaches flood recovery programs, the branch
  or managers; those have their own side-by-side tests, but a stronger bot would cover them in whole careers too.
